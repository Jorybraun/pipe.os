# Security Audit — 2026-03-25

**Auditor:** Claude (automated) + Hans (review)
**Scope:** Amplify Data authorization rules, Lambda resolvers, S3 storage access, candidate authentication flow
**Codebase version:** `main` branch, commit `b925b50`

---

## Executive Summary

The Pipe platform uses AWS Amplify Gen 2 with Cognito (recruiter auth) and publicApiKey (unauthenticated candidate access). The audit found **3 critical**, **2 high**, and **3 medium** severity issues. Two critical issues have been fixed in this session. The remaining issues are documented with remediation plans.

---

## Trust Boundaries

```
Recruiter (Cognito userPool) ──> AppSync ──> DynamoDB
                                    ^
Candidate (publicApiKey)  ──────────┘
                                    ^
Anyone (guest/unauthenticated) ─────┘
```

**Rule:** Pipeline ownership is the trust boundary. Only the recruiter who created a pipeline should see its candidates, assessments, stages, challenges, and media.

## Findings

### CRITICAL — P0

#### P0-001: Cross-candidate assessment forgery (FIXED)

| Field | Value |
|---|---|
| **Model** | Assessment |
| **Rule** | `allow.publicApiKey().to(["create", "update"])` |
| **Status** | **FIXED** |

**Description:** The Assessment model allowed any API-key holder to create assessments for any `candidateId`. A candidate with one valid invite token could forge assessments attributed to other candidates.

**Attack vector:** Call `Assessment.create({ candidateId: "victim-id", submission: "..." })` using the publicApiKey visible in the client bundle.

**Fix applied:** Created `submitAssessment` Lambda resolver (`amplify/functions/createAssessment/`) that:
1. Accepts `inviteToken` as the sole identity proof (not candidateId)
2. Resolves candidateId server-side from DynamoDB
3. Sets `ownerId` from the Candidate record's `owner` field
4. Rejects duplicate assessments (same candidate + challenge)
5. Ignores any client-supplied `candidateId` or `ownerId`

**Tests:** 11 unit tests covering validation, token rejection, forgery prevention, duplicates, edge cases. All passing.

**Files changed:**
- `amplify/functions/createAssessment/handler.ts` (new)
- `amplify/functions/createAssessment/handler.test.ts` (new)
- `amplify/functions/createAssessment/resource.ts` (new)
- `amplify/data/resource.ts` (added `submitAssessment` mutation)
- `amplify/backend.ts` (wired Lambda to DynamoDB tables)
- `src/hooks/useAssessment.ts` (switched to `submitAssessment` mutation)

**Residual risk:** The `publicApiKey` create/update rule on the Assessment model is still present for backward compatibility. It should be removed once the `submitAssessment` mutation is confirmed working in production. The `update` path (for follow-up answers) still needs a Lambda resolver.

#### P0-002: Recruiter Cognito sub leaked to candidate clients (FIXED)

| Field | Value |
|---|---|
| **Endpoint** | `resolveToken` query |
| **Data leaked** | `ownerId` (recruiter's Cognito sub) |
| **Status** | **FIXED** |

**Description:** The `resolveToken` Lambda returned the recruiter's Cognito sub (`owner` field from the Candidate record) to the candidate client as `ownerId`. This internal identifier was then sent back by the client when creating assessments.

**Attack vector:** Any candidate can observe the recruiter's Cognito sub in network traffic. Combined with P0-001, this enabled complete assessment forgery with correct ownership attribution.

**Fix applied:**
1. Removed `ownerId` from `resolveToken` return type (schema + Lambda handler)
2. Removed `owner` from DynamoDB ProjectionExpression in the Lambda
3. `ownerId` is now set server-side by the `submitAssessment` Lambda
4. Removed `ownerId` from `ResolvedCandidate` interface in `useAssessment.ts`

**Files changed:**
- `amplify/functions/resolveToken/handler.ts`
- `amplify/data/resource.ts` (resolveToken return type)
- `src/hooks/useAssessment.ts`

#### P0-003: Assessment.publicApiKey update is unscoped (OPEN)

| Field | Value |
|---|---|
| **Model** | Assessment |
| **Rule** | `allow.publicApiKey().to(["update"])` |
| **Status** | **OPEN** |

**Description:** Any API-key holder can update any Assessment record. This is used for follow-up answers (`followUpQuestionsJson`), but there is no server-side validation that the caller owns the assessment.

**Attack vector:** Call `Assessment.update({ id: "any-assessment-id", score: 100 })`.

**Remediation:** Build `updateAssessmentFollowUp` Lambda resolver that accepts `inviteToken` + `assessmentId` + `followUpAnswers`, validates the token matches the assessment's candidate, and only updates `followUpQuestionsJson`.

### HIGH — P1

#### P1-001: VideoSignal readable by any recruiter (OPEN)

| Field | Value |
|---|---|
| **Model** | VideoSignal |
| **Rule** | `allow.authenticated().to(["read"])` |
| **Status** | **OPEN — accepted risk** |

**Description:** Any authenticated recruiter in the Cognito pool can read VideoSignal records from any video session. Signals contain WebRTC SDP offers/answers and ICE candidates.

**Mitigation:** Session IDs are UUIDv4 (not enumerable). Signals are ephemeral. Data sensitivity is low (browser/OS fingerprint in SDP, NAT addresses in ICE candidates).

**Remediation:** Requires session-token architecture or an opaque session key (not recruiter Cognito sub) to scope reads without exposing internal IDs.

---

#### P1-002: fetchGitHubPR allows unauthenticated access (OPEN)

| Field | Value |
|---|---|
| **Mutation** | `fetchGitHubPR` |
| **Rule** | `allow.publicApiKey()` |
| **Status** | **OPEN** |

**Description:** Any API-key holder can call `fetchGitHubPR` with any `repoUrl` and `prNumber`. If the platform's GitHub token has access to private repositories, this leaks PR data.

**Current usage:** Candidates call this to load PR diffs on-demand in `ChallengeRegistry.tsx` for CODE_REVIEW challenges.

**Remediation:** Either:
- Cache diffs on challenge creation and serve from the Challenge record (eliminates candidate need to call this)
- Add a session-token gate that validates the candidate has an active assessment for the relevant challenge

### MEDIUM — P2

#### P2-001: Candidate.publicApiKey update is unscoped (OPEN)

| Field | Value |
|---|---|
| **Model** | Candidate |
| **Rule** | `allow.publicApiKey().to(["update"])` |
| **Status** | **OPEN** |

**Description:** Any API-key holder can update any Candidate record's status, `currentStageId`, etc. Used by the candidate flow to set status to `IN_PROGRESS` / `COMPLETED`.

**Remediation:** Build `updateCandidateStatus(inviteToken, status)` Lambda resolver.

---

#### P2-002: DynamoDB IDs exposed to candidate clients (OPEN)

| Field | Value |
|---|---|
| **Endpoint** | `resolveToken` query |
| **Data exposed** | `id` (candidate DynamoDB UUID), `pipelineId` (pipeline DynamoDB UUID) |
| **Status** | **OPEN** |

**Description:** `resolveToken` returns the candidate's DynamoDB ID and pipeline ID to the client. These are used for stage queries and candidate status updates. While UUIDs are not guessable, exposing internal IDs violates the principle of not sending internal identifiers to untrusted clients.

**Current usage:**
- `candidate.id` — `Candidate.update({ id, status })` (status updates)
- `candidate.pipelineId` — `Stage.list({ filter: { pipelineId } })` (load stages)

**Remediation:** Build Lambda resolvers for:
- `updateCandidateStatus(inviteToken, status)` — replaces direct Candidate.update
- `loadPipelineStages(inviteToken)` — replaces Stage.list with pipelineId filter

Then remove `id` and `pipelineId` from resolveToken return. The inviteToken becomes the sole identity proof for all candidate operations.

---

#### P2-003: S3 challenge-questions readable by guests (OPEN)

| Field | Value |
|---|---|
| **Path** | `challenge-questions/*` |
| **Rule** | `allow.guest.to(["read"])` |
| **Status** | **OPEN — accepted risk** |

**Description:** Unauthenticated users can read recruiter-uploaded question media (e.g., video prompts for challenges) from S3.

**Mitigation:** Paths use challenge IDs (UUIDv4), making enumeration difficult. Content is intentionally shown to candidates during assessment.

**Remediation:** Move to presigned URLs issued by a Lambda that validates the candidate has an active assessment for the challenge.

## Remediation Roadmap

### Phase A — Done (this session)
- [x] `submitAssessment` Lambda resolver (P0-001)
- [x] Remove ownerId from resolveToken (P0-002)
- [x] 11 unit tests for createAssessment handler

### Phase B — Next priority
- [ ] `updateAssessmentFollowUp` Lambda resolver (P0-003)
- [ ] `updateCandidateStatus(inviteToken, status)` Lambda resolver (P2-001)
- [ ] Remove `publicApiKey` create/update from Assessment model (after Phase B deploy confirmed)

### Phase C — Session token architecture
- [ ] `resolveToken` returns a signed short-lived JWT instead of raw IDs
- [ ] All candidate mutations validate the JWT server-side
- [ ] `loadPipelineStages(inviteToken)` Lambda resolver (P2-002)
- [ ] Remove `id` and `pipelineId` from resolveToken return
- [ ] inviteToken marked as "claimed" after first use

### Phase D — Hardening
- [ ] Rate limiting on publicApiKey operations (resolveToken, submitAssessment)
- [ ] Cache PR diffs at challenge creation time, remove publicApiKey from fetchGitHubPR (P1-002)
- [ ] Replace guest S3 read with presigned URLs (P2-003)
- [ ] API key rotation schedule
- [ ] `generateMediaUploadUrl` validates inviteToken, not just candidateId existence
