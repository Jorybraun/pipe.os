## Summary
Fixed critical WebRTC connection failure preventing video interviews from establishing. Root cause was auth asymmetry where recruiter couldn't read candidate's signals due to missing `allow.authenticated()` rule. Also implemented deferred accept pattern, added connecting state UI, and fixed inverted drag positioning.

## Key Changes for Review

### 1. Schema Authorization (BREAKING CHANGE) ⚠️
**File:** `amplify/data/resource.ts` (lines 103-112)

**Change:** Added `allow.authenticated().to(['read'])` to VideoSignal model

**Rationale:** 
- Candidate creates signals via `apiKey` auth (no Cognito owner)
- Recruiter subscribes via `userPool` auth
- AppSync auth checks happen per-record before subscription filters
- Without authenticated read permission, signals never reach recruiter's subscription

**Risk Assessment:**
- 🔴 **BREAKING:** Requires `npx ampx sandbox` redeploy
- 🟡 **Security:** Broadens read access to all authenticated users (acceptable for video signals)
- 🟢 **Rollback:** Simple revert + redeploy (but breaks active calls)

**Review Focus:**
- Is `allow.authenticated().to(['read'])` the right authorization model?
- Should we use `allow.groups(['recruiters'])` instead for tighter control?
- Are there any other signals we need to protect from authenticated read access?

### 2. Deferred Accept Pattern
**File:** `src/components/Shells/VideoShell.tsx` (lines 78-79, 117-139, 193-209)

**Change:** Store incoming OFFER in ref, add `hasPendingOffer` state, create `handleAccept` callback

**Before:**
```typescript
case "OFFER":
  await acceptCall(JSON.parse(signal.payload));
  await markActive();
  break;
```

**After:**
```typescript
case "OFFER":
  pendingOfferRef.current = JSON.parse(signal.payload);
  setHasPendingOffer(true);
  break;

const handleAccept = async () => {
  if (!pendingOfferRef.current) return;
  if (!localStream) { /* ensure camera */ }
  await acceptCall(pendingOfferRef.current);
  await markActive();
};
```

**Rationale:** UI should not change automatically on signal arrival - user must explicitly click ACCEPT

**Risk Assessment:**
- 🟢 **Low Risk:** Purely UX improvement, no functional changes to WebRTC negotiation
- 🟡 **Edge Case:** What if user never clicks ACCEPT? (Timeout handling out of scope)

**Review Focus:**
- Does `pendingOfferRef` need cleanup logic if component unmounts?
- Should there be a timeout that resets `hasPendingOffer` after N seconds?

### 5. Drag Positioning Fix
**File:** `src/components/Video/VideoFloatingPiP.tsx` (lines 43-52, 97)

**Change:** Switched from `right: position.x` to `left: position.x`, recalculated initial position

**Before:**

// ...

**After:**

**Rationale:** Position state stored left-based coordinates but style used right property

## Security Review
- 🟡 **Auth Change:** `allow.authenticated()` grants read access to all logged-in users
  - **Concern:** Recruiter A could theoretically read Recruiter B's call signals if they guess the sessionId
  - **Mitigation:** SessionId is UUID v4 (128-bit entropy), signals include stageId + candidateId context
  - **Recommendation:** Consider adding owner-based read for same-session users only

- 🟢 **No XSS:** All signal payloads are JSON-serialized (no HTML rendering)
- 🟢 **No CSRF:** GraphQL mutations use Amplify auth tokens
- 🟢 **No Injection:** ICE candidates are WebRTC-native objects, not user input
