## Architecture Decision Record: ADR-015 - Adaptive Notification Engine

**1. Status:** Proposed

**2. Context:**

The Pipe platform requires a robust and adaptable notification system to automate candidate communications (Success, Failure, Scheduling) triggered by stage transitions.  Currently, notification logic resides within the frontend, leading to tight coupling and difficulty in customization.  We need to decouple notification logic from the frontend and provide a mechanism for recruiters to customize emails per-stage through the UI.

**3. Decision:**

We will implement an adaptive notification engine using the following components:

*   **Trigger:** DynamoDB Stream on the `Stage` and `Pipeline` models.
*   **Processing:** A `notificationAgent` Lambda function.
*   **Delivery:** AWS SES (Simple Email Service) for email delivery.
*   **Variable Substitution:** A template engine within the `notificationAgent` to handle variable substitution (e.g., `{{name}}`, `{{bookingUrl}}`).

**Rationale for DynamoDB Stream vs. AppSync hooks:**

*   **DynamoDB Streams:**
    *   **Pros:**  Asynchronous, reliable, and decoupled.  Guaranteed delivery (at least once).  Handles high volumes of updates efficiently.  Provides a clear audit trail of changes.  Better suited for background processing.
    *   **Cons:**  Increased latency compared to synchronous AppSync hooks.  Requires managing stream processing and potential retries.
*   **AppSync Hooks:**
    *   **Pros:**  Synchronous, low latency.  Simpler to implement initially.
    *   **Cons:**  Tight coupling to the AppSync API.  Potential performance impact on API operations.  Less reliable for guaranteed delivery.  Difficult to scale for high volumes of updates.  Can lead to complex authorization logic within the data layer.

    **Decision:** We chose DynamoDB Streams for their reliability, scalability, and decoupling benefits.  The increased latency is acceptable for this use case, as immediate notification is not critical. DynamoDB Streams allow for asynchronous processing and better error handling.

**Design of the variable substitution system:**

The `notificationAgent` Lambda function will implement a template engine to support variable substitution within email templates. The template engine will use a simple syntax (e.g., `{{variableName}}`) to identify variables within the template.

The following variables will be supported:

*   `{{name}}`: Candidate name.
*   `{{stageName}}`: Name of the stage.
*   `{{pipelineName}}`: Name of the pipeline.
*   `{{status}}`:  New status of the stage (e.g., "Passed", "Failed").
*   `{{bookingUrl}}`:  URL for scheduling an interview (generated by Calendly or Cal.com).
*   `{{recruiterName}}`: Name of the recruiter associated with the pipeline.
*   `{{companyName}}`: Name of the company.

The variable substitution system will:

*   Fetch necessary data (candidate details, stage details, etc.) from DynamoDB.
*   Replace variables in the template with their corresponding values.
*   Handle missing variables gracefully (e.g., by logging an error or using a default value).
*   Support custom variables defined in the UI.

**Integration with AWS SES:**

The `notificationAgent` Lambda function will use the AWS SES SDK to send emails.  We will configure SES with appropriate DKIM and SPF records to ensure high deliverability. We will also implement bounce and complaint handling to maintain a good sender reputation.

We will use the SES SendEmail API to send emails with HTML and plain text content. The `notificationAgent` will:

*   Compose the email using the rendered template.
*   Set the sender address, recipient address, subject, and body.
*   Call the SES SendEmail API.
*   Log the email sending status.
*   Handle SES errors (e.g., sending failures, throttling).

**4. Consequences:**

*   The notification logic is decoupled from the frontend, improving maintainability and flexibility.
*   Recruiters can customize email templates per-stage in the UI, enabling personalized candidate communications.
*   The DynamoDB Stream architecture provides reliable and scalable notification processing.
*   The SES integration ensures high email deliverability.
*   The variable substitution system supports dynamic content in email templates.
*   The system introduces a new Lambda function and requires ongoing monitoring and maintenance.

**5. Alternatives Considered:**

*   AppSync hooks (rejected due to tight coupling and scalability concerns).
*   Custom messaging queue (rejected due to complexity and lack of AWS integration).
*   Direct SES calls from the frontend (rejected due to security and maintainability concerns).
