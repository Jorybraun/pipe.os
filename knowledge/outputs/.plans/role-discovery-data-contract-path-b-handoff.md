## What Path B is

Path B is the **repo-understanding branch** of ADR-036's rollout. Path A (culture-first) chose Phase 1 → Phase 2 because it has the smallest blast radius. Path B is the alternative that was deferred, not killed: **Phase 1 → Phase 4 → Phase 3**. The founder asked for a parallel agent to run Path B because Phase 4 is entirely independent of Phase 2's culture work, and the RCD schema is already frozen in `types.ts` — so a parallel agent can build Phase 4 from the schema without blocking on Path A's synthesis producer.

Why this parallelization is safe:

- **Phase 4's first three steps are entirely offline and role-agnostic.** The crawler Pass 3 summarization, the `persist.ts` writer, and the Queue consumer wiring never read the RCD at all. They populate `repo_engineering_signals` with role-agnostic features (language distributions, test density, PR cadence, etc.) per the research brief's argument that signal extraction must precede query-conditional reranking. You can build and land these three steps **without Phase 1 synthesis working at all** — you only need the D1 table (already shipped in migration 0022).
- **Phase 4 steps 4+ (`roleFitRerank.ts`, `discover.ts` injection, `explainRepoForRole` copilot tool) need the RCD at runtime.** But by the time you land steps 1–3 and start on step 4, Path A will have finished Phase 1 and you can consume real RCDs. If you happen to get to step 4 before Phase 1 lands, you can still build it against the frozen types and seed a test fixture RCD manually.
- **Phase 3 (code review consumer rewrite)** is the other half of Path B. It touches `challengeGeneration/prompts.ts`, `implementerAgent.ts`, and `scorerAgent.ts`. These are different files from Path A's culture consumer work (`cultureRoleResolution.ts`, `cultureQuestionBank.ts`, `cultureScorer.ts`), so no merge-conflict risk.

**Your scope is Phase 4 + Phase 3, in that order.** Stop after Phase 3's BDD test passes and hand back to the founder. Do not touch Phase 2.

## Phase 4 — Repo understanding (your primary slice)

Reference: ADR-036 §"Phase 4 — Repo understanding" (line 492), research brief Half 2, STRATEGY.md RD-23 + RD-24.

### The two-stage retrieval architecture, in one paragraph

The current state is that `workers/api/src/lib/repoDiscovery/matchRepos.ts` is a SQL CTE join on `persona.mustHaveSkills[]` — a deterministic keyword match with no reasoning layer. The research brief argues this is identical to the query-agnostic retrieval baseline that SWE-bench showed has meaningfully limited recovery rates at realistic context sizes, and that the fix (grounded in ColBERT's offline/online split and AIF's decoupled preranking) is a two-stage architecture: an **offline pass** that extracts role-agnostic engineering signals from each repo once, cached forever, and a **runtime rerank pass** that takes a query (here, an RCD) and reranks candidate repos against those signals using a small but query-aware model. Pass 3 is the offline signal extraction. `roleFitRerank.ts` is the runtime reranker. `matchRepos` stays the fast SQL stage-0 filter but returns 20 candidates instead of a hard top-N so the reranker has a real candidate pool to work with.

### Model routing

Per ADR-036's model routing table and CLAUDE.md's AI model routing section:

- **Pass 3 summarization (offline, batch):** Claude Haiku 4.5 via the Agent tool (the offline Claude Code path). This is **not** on the Worker hot path. It runs as a Node script invoked by the Queue consumer, reads repo metadata from D1, summarizes with Haiku, writes `repo_engineering_signals` rows. Follow the same "build-time vs. runtime" pattern CLAUDE.md describes — Workers cannot call Claude directly on the hot path, but offline scripts can use the Agent tool path.
- **Runtime rerank:** **Gemma 4 26B** via the existing `CloudflareAIProvider` on Workers AI. This is on the hot path (recruiter clicks "discover repos" and waits), so it must stay inside the Worker and use the Workers AI binding. **Do not introduce a new AnthropicProvider for the rerank.** Same rule as the Phase 1 verifier transport decision.
- **Model-family independence:** Haiku writes the signals. Gemma reads them and reranks. Different families — intentional. Per the research brief's anchor to ADR-032's implementer/classifier separation principle, **never use Haiku to rerank Haiku-generated signals**. If you ever swap either model, verify family independence before shipping.

### File-by-file breakdown

1. **`workers/api/scripts/crawl-repos/pass3/summarize.ts`** — Haiku 4.5 per-repo summarization. Input: repo metadata row from D1 (existing Pass 1/Pass 2 output). Output: a `RepoEngineeringSignals` object matching the type in `workers/api/src/types.ts`. Follow the existing crawler pattern in `workers/api/scripts/crawl-repos/` — Pass 1 and Pass 2 are already there, read their entrypoints to see the script convention. The summarization prompt itself needs to be grounded in the research brief's §"codebase signals" section (RD-17 through RD-22) — it should extract: language distribution, test-to-code ratio, PR review cadence, docs density, dependency modernity, architectural style signals (monorepo vs polyrepo, etc.), and the free-text `engineering_notes` field. Read the research brief before writing the prompt.

2. **`workers/api/scripts/crawl-repos/pass3/persist.ts`** — writes `repo_engineering_signals` rows to D1. Idempotent on `repo_url` + content hash (re-running the crawler on an unchanged repo should be a no-op). Follow the existing Pass 2 persistence pattern. **Content hashing is mandatory** — per the research brief it's the only way to keep crawler runs cheap as the repo pool grows. Hash the inputs that matter (language manifest + test file count + PR metadata window) and skip the Haiku call if the hash matches the existing row.

3. **Cloudflare Queue consumer wiring** — trigger Pass 3 when Pass 2 completes for a repo. Look at `wrangler.toml` for existing queue bindings. If Pass 1/Pass 2 already fire queue messages on completion, add a Pass 3 consumer. If they don't, this is a bigger change — in that case, write Pass 3 as a cron-triggered batch job instead (read all repos where `pass3_completed_at IS NULL` and summarize in batches). **Pick the simpler option** unless the existing queue wiring is already there. Do not build queue infrastructure for its own sake.

4. **`workers/api/src/lib/repoDiscovery/roleFitRerank.ts`** — the runtime rerank handler. **This is the core of Path B.** Signature roughly:
   ```typescript
   export async function roleFitRerank(opts: {
     rcd: RoleContextDocument;
     candidates: Array<{ repo_url: string; signals: RepoEngineeringSignals }>;
     provider: CloudflareAIProvider;
   }): Promise<RepoRoleAlignment[]>
   ```
   It builds a prompt from the RCD's `technical_context` + `domain_matrix['work'/'codebase']` cells + the candidate signals, calls Gemma 4 26B with structured JSON output, and returns one `RepoRoleAlignment` per candidate with a `score`, `reasoning_json` (what matched, what didn't), and a `justification` string that references specific RCD fields. **Critical:** the justification must reference specific RCD `technical_context` fields by name (e.g. "stack: TypeScript, Node 20" or "codebase_expectations: monorepo"). This is the test assertion the BDD uses to verify the rerank actually consumed the RCD and didn't just rank-by-stars.

5. **`workers/api/src/lib/repoDiscovery/discover.ts`** — inject `roleFitRerank` between `matchRepos` (stage 0) and the final ranked result. Current `discover.ts` calls `matchRepos` and returns. New version: call `matchRepos` for up to 20 candidates, fetch their `repo_engineering_signals`, call `roleFitRerank` against the RCD, write `repo_role_alignment` rows (cached forever keyed on `rcd_version` + `repo_url`), return the top-5 ranked by `score`. Cache hit path: if `repo_role_alignment` already has rows for this `(rcd_version, repo_url)` set, skip the Gemma call entirely and read cached reasoning.

6. **`workers/api/src/lib/repoDiscovery/matchRepos.ts`** — unchanged at the SQL level but change the top-N limit from whatever it is now to 20. Verify nothing downstream depends on the exact count before making the change.

7. **`workers/api/src/lib/copilot/tools/explainRepoForRole.ts`** — new copilot tool per ADR-035's tool protocol. Read the existing tools in `workers/api/src/lib/copilot/tools/` first to see the registration pattern, tool schema, and the drawer UI contract. This tool takes `{ repo_url, role_context_id }`, looks up `repo_role_alignment.reasoning_json`, and returns a structured explanation the recruiter drawer can render.

### BDD test for Phase 4

Per CLAUDE.md's route-based BDD-first rule, write the test first. Vitest REST test, in the `workers/api/tests/` directory or wherever the existing repo discovery tests live. Seeded fixture: one `RoleContextDocument` with populated `technical_context` (stack: TypeScript/Node, codebase_expectations: monorepo), three seeded repos in D1 with populated `repo_engineering_signals` (one strong match, one weak match, one irrelevant). 1. `discover` on the seeded RCD returns the strong-match repo first.

3. A second call to `discover` with the same RCD hits the cache — zero Gemma calls (assert via a provider mock or a call counter).
4. The `explain_repo_for_role` copilot tool returns a structured response with the same `reasoning_json` shape.

Write the test. Watch it fail. Build until it passes. Commit.

## Phase 3 — Code review consumer rewrite (your secondary slice)

Reference: ADR-036 §"Phase 3 — Code review consumer rewrite" (line 483), STRATEGY.md RD-17 through RD-19.

**Do not start Phase 3 until Path A's Phase 1 has landed.** Check that `synthesizeRcd.ts` is committed on the branch and that the Phase 1 BDD test is green before you touch Phase 3 files. The reason: Phase 3 consumes the RCD at runtime from challenge generation and scoring, so you need the synthesis producer working end-to-end to test it.

Phase 3 touches three files:

1. **`workers/api/src/lib/challengeGeneration/prompts.ts`** — currently reads 5 fields from the flat `CandidatePersona`. Rewrite to read `technical_context` from the RCD instead. The existing 5 fields map roughly to: `technical_context.stack` (languages, frameworks), `technical_context.seniority_band` (seniority), `technical_context.codebase_expectations` (architectural fit), plus the work/codebase `DomainCell` summaries for the free-text context. Preserve the exact prompt shape — just swap the data source. Grep the test files before changing the prompt structure; there are likely golden-file tests on the prompt output that need updating.

2. **`workers/api/src/lib/implementerAgent.ts`** — inject role context into the implementer persona YAML resolution per ADR-032. Specifically: the `technical_context.dispositional_weights` object should feed into how the implementer persona is tuned (e.g. if the role weights "pragmatism" heavily, the implementer's pushback style shifts). Read ADR-032 first to understand the existing persona YAML structure and where to inject. The research brief §"Half 1 — Role Context Document" explains why dispositional weights flow into the implementer specifically: the implementer's rebuttal behavior should match what this particular role rewards.

3. **`workers/api/src/lib/scorerAgent.ts`** — read dispositional context for per-dimension weight adjustments per ADR-032's 6-dimension rubric. This is the biggest change of the three: the scorer currently applies uniform weights across all 6 dimensions. Phase 3 makes it read `technical_context.dispositional_weights` and scale each dimension's contribution by the RCD-derived weight. The important constraint from the research brief: **weights can only shift magnitudes, never signs**. A role cannot "turn off" a dimension — communication quality still matters even if the role weights pragmatism over rigor. Enforce this in the weight-application logic (clamp all weights to `[0.5, 1.5]` or similar).

### BDD test for Phase 3

Vitest REST test. Seeded fixture: one full RCD with a distinctive `technical_context` (e.g. `stack: ['Rust', 'WebAssembly']`, `dispositional_weights: { pragmatism: 1.3, rigor: 0.8 }`). Test assertions:

1. A challenge generated from this RCD has a prompt that contains the verbatim string `Rust` or `WebAssembly`.
2. The scorer applied to a mock review conversation produces per-dimension scores where the `pragmatism`-related dimension is weighted higher than the `rigor`-related dimension compared to the baseline.
3. The scorer never clamps any dimension to zero (sign-preservation check).

Write the test. Watch it fail. Build until it passes. Commit.

## Constraints you must not drop

These come from CLAUDE.md, the Phase 1 kickoff decisions in the implementation handoff, and the research guardrails. They apply to your work too.

**No new secrets or transports on the Worker hot path.** The runtime rerank must use the existing `CloudflareAIProvider` and the existing Workers AI binding. Do not add an `AnthropicProvider` or new `ANTHROPIC_API_KEY`-equivalent for runtime use. Offline crawler scripts (Pass 3) can use the Agent tool path for Haiku calls, since that's the already-established offline Claude Code pattern documented in CLAUDE.md.

**Model-family independence.** Haiku writes signals. Gemma reranks. Never cross the streams. If you swap either model, verify the replacement is from a different family before merging.

**Content hashing on Pass 3.** Non-negotiable. Without it, re-crawling the repo pool costs real money on Haiku for unchanged repos. Hash the inputs that actually determine the summary (language manifest, test file count, recent PR metadata window) and skip the call if the hash is unchanged.

**`rcd_version` + `signals_version` are load-bearing for caching.** `repo_role_alignment` must key on `(rcd_version, repo_url, signals_version)`. When either version bumps, the cache invalidates. Never cache on `role_context_id` alone — it'll poison the cache the moment an RCD is re-synthesized with a different prompt version. See the implementation handoff §"Versioning precondition is not optional" for why this matters for the staged validation ladder.

**No auto-fail on dealbreakers, no auto-anything on compliance surfaces.** Phase 4 doesn't touch dealbreakers directly, but the copilot tool `explain_repo_for_role` surfaces reasoning about fit — it must never phrase a repo as "disqualified" or "rejected". The tool explains fit; the recruiter decides. This matches ADR-031's HITL-only gate pattern.

**TypeScript strict mode, no `any`.** Use `unknown` + type guards. Explicit return types on all exported functions. Named exports. Run `npx tsc --noEmit` before every commit. **Never pipe tsc output through `head` or `tail`** — it masks the exit code (explicit CLAUDE.md rule).

**CHANGELOG.md under `[Unreleased]` on every source commit** — enforced by the pre-commit hook.

**Update STRATEGY.md** — mark RD-17, RD-18, RD-19, RD-23, and RD-24 as complete with the commit SHA once each phase lands. Also add a Decision Log entry at the bottom of STRATEGY.md for Path B's start/finish with the date and any deviations from the ADR.

**Any contradiction with the research brief must be flagged before coded.** This is the ADR-033 guardrail. If something you're building doesn't match what the brief says, pause, name the finding being overridden by its RD-row, ask for explicit override, and record it in the STRATEGY.md Decision Log.
